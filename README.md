# AI와 함께하는 게임 한글화 파이프라인

Claude(Claude Code)와 GPT(이미지 생성)로 여러 기종의 게임을 한글화하면서 정리한 작업 순서와 규칙이다.
3DS·NDS·GC·Wii·Wii U·SFC 게임 스무 편 남짓을 진행하며 실제로 겪은 실패와 해결을 바탕으로 했다.

- 대상: AI에게 분석·추출·번역·그래픽·빌드를 맡기는 개인 한글화 작업자
- 전제: 게임 원본은 직접 가진 것을 쓰고, 배포물에는 게임 데이터를 넣지 않는다.
- 같은 내용을 Claude Code 스킬로도 만들어 두었다(`skill/game-localization-pipeline/`).

**모든 게임에 똑같이 적용하지 않는다.** 게임마다 한글화할 분야(텍스트·폰트·그림·이펙트·3D 모델·영상·음성 자막 등)와 파일 구조(롬 하나, 디스크 이미지, 여러 아카이브), 실행 환경(실기·에뮬레이터)이 다르다.
1단계 분석에서 **이 게임의 분야 목록과 실행 환경**을 정하고, 이후 단계는 그 목록에 있는 것에만 적용한다. 해당 없는 항목은 건너뛰고 이유를 한 줄 남긴다.

게임마다 달라지는 대표적인 경우:
- **텍스트가 전부 그림인 게임**: 폰트·창 측정 대신 그림 교체 시험으로 2·3단계를 대신한다(그림 한 장을 한글로 바꿔 띄워 보고, 그림 칸 크기를 잰다).
- **롬 파일 하나인 구형 기종**: 교체 단위가 없으니 빌드 옵션으로 분야를 켜고 끈다. 포인터·빈 공간 부족이 주된 난관이다.
- **3D 모델·영상·음성 자막이 없는 게임**: 해당 추출·빌드·점검을 모두 건너뛴다.
- **화자 정보가 없는 게임**: 대사 순서와 장면으로 화자를 추정하거나 비워 둔다.

## 0. 준비

- **판본을 먼저 정한다.** 일본판·북미판·유럽판 중 어느 쪽에 넣을지에 따라 폰트 용량, 글 창 크기, 번역 원문이 달라진다.
  - 원문은 일본어로 두고 그릇은 다른 지역판을 쓰는 경우도 있다(예: 일본어 원문을 번역해 유럽판에 넣음).
  - 이미 나온 한글 패치가 있는지 먼저 찾아본다.
- **원본 해시를 기록한다.** 덤프·변환 방식에 따라 같은 게임도 해시가 다르다. 나중에 배포 방식을 정할 때 필요하다.
- **처음부터 git 저장소로 시작한다.**
  - 추적하는 것: 도구, 번역 원본(JSON 등), 목록 파일, 문서
  - 추적하지 않는 것: 게임 데이터, 게임 그림이 든 이미지, 빌드 산출물
  - 그림은 git에 없으니 덮어쓰거나 지우면 되살릴 수 없다. 확정본 폴더는 따로 백업한다.
- **작업 규칙 파일(`CLAUDE.md` 등)을 만든다.** 세션이 바뀌어도 같은 규칙으로 일하도록 폴더 구조, 빌드 명령, 금지 사항, 현재 상태를 적어 둔다.

## 1. 분석·난이도 판정

AI에게 아래 항목을 표로 받는다.

| 항목 | 볼 것 |
|---|---|
| 텍스트 | 형식(MSBT·BMG 등), 인코딩, 메시지 수, 순수 글자 수, 태그 종류 |
| 폰트 | 형식, 글리프 칸 수, 한글 약 2,350자가 들어갈 자리가 있는지, 고정폭 여부 |
| 그래픽 | 글자가 박힌 그림 수, 텍스처 형식, 압축·스위즐 |
| 컨테이너 | 아카이브·압축 형식, 체크섬·서명, 파일 크기 제한 |
| 재삽입 | 원본을 풀었다가 바꾸지 않고 다시 묶었을 때 **원본과 바이트까지 같은지** |
| 분야 목록 | 이 게임에서 한글화할 분야(텍스트·폰트·그림·이펙트·3D 모델·영상 등 중 **있는 것만**)와 분야별 파일 위치 |
| 실행 환경 | 배포 대상(실기·에뮬레이터 종류), 원본을 넣는 방식(롬 교체·파일 치환 플러그인·재빌드 등) |

- 마지막 항목(무변경 왕복)이 가장 중요하다. 바꾸지 않고 다시 묶은 결과가 원본과 같아야 이후 문제가 생겼을 때 원인을 좁힐 수 있다.
- **불가능·불투명**이면 진행하지 않는다. 분석에서 배울 만한 내용(형식 구조, 함정)만 기록으로 남긴다.
  - 분량이 너무 많은 것도 중단 사유다. 글자 수와 작업 시간을 현실적으로 따진다.

## 2. 한글 출력 시험

- 게임 초반에 반드시 나오는 문구 몇 개만 한글로 바꿔서 띄워 본다.
- **배포 대상 환경에서 모두** 본다. 실기로도 배포할 거라면 실기에서 꼭 확인한다. 에뮬레이터에서 멀쩡한데 실기에서 멈추는 경우가 있다.
  - 실기가 없으면 정확도가 다른 에뮬레이터 두 가지 이상으로 확인하고, 실기 미확인이라고 문서에 적는다.
  - 사례: 아카이브(CPK) 안 파일을 무압축으로 바꿔 넣었더니 에뮬레이터는 정상이었지만 실기는 로고 뒤에 멈췄다. 원본처럼 압축해 넣으니 해결됐다.
- 한글이 안 나오면 원인은 보통 글리프가 없거나(빈칸·□), 인코딩이 틀렸거나, 태그가 깨진 것이다.

## 3. 글 창 크기 측정

- 창 종류마다 따로 잰다: 대사창, 도움말, 선택지, 알림, 아이템 설명 등.
- **글자 수가 아니라 픽셀로** 잰다. 한 줄 최대 폭(px), 줄 수 한도, 글자별 폭을 기록한다.
  - 원문의 가장 긴 줄이 기준이 된다.
- **고정폭 폰트를 조심한다.** 일본어 게임 폰트는 반각 띄어쓰기·쉼표·느낌표도 전각 한 칸을 차지하는 경우가 있다. 한국어는 띄어쓰기가 많아 한 줄이 크게 길어진다. 폰트의 글자 폭을 조정하거나 줄바꿈을 다시 해야 한다.
- 측정값으로 **자동 넘침 검사 도구**를 만들어 두고, 번역할 때마다 돌린다.

## 4. 전수 추출

"전부 뽑아 달라"고만 하면 빠지는 곳이 생긴다. **조사할 곳을 목록으로 주고, 조사한 범위를 표로 받는다.**

아래는 **후보 목록**이다. 게임에 있는지 하나씩 확인하고, 없으면 「없음」으로 표에 적는다(빠뜨린 것과 없는 것을 구분하기 위해).
- 텍스트: 대사 파일 전부 + 스크립트·표·실행 파일 속 문자열
- 그래픽: UI 텍스처, 배경 속 간판, 이펙트·파티클 텍스처, 3D 모델 텍스처, 타일·스프라이트(구형 기종)
- 영상·음성: 자막, 영상 속 글자(타이틀 로고 등)
- 교차 확인: 다른 지역판이 있으면 그 판이 번역한 곳 = 화면에 나오는 곳이다. 다른 지역판도 그대로 둔 원문은 개발용일 가능성이 크다.

텍스트는 JSON(또는 xlsx)으로 받는다.
- 키: 파일, 라벨(또는 인덱스), 원문, 번역
- 가능하면 **화자명**을 함께 뽑는다. 화자를 알아야 말투를 맞출 수 있다.
- 번역 파일에서 원본을 다시 만드는 왕복이 원본과 같은지 확인한다.

그래픽은 원본 크기의 래스터 이미지(PNG)로 받고, 목록 파일(경로·형식·크기·상태)을 하나 만든다.

## 5. 용어집 → 텍스트 번역

- **용어집을 먼저 만든다.** 인물명, 지명, 기술명, 작품 속 고유명사, 호칭, 말투.
  - 공식 한국어 명칭이 있으면 그것을 따른다(정발작, 같은 시리즈의 한국어판).
  - 공식 사이트·위키·팬 사이트에서 설정을 확인한다.
- **화자별 말투표**를 만든다(반말·존댓말, 1인칭, 버릇, 누구를 뭐라고 부르는지).
- 번역을 맡길 때 문장부호 규칙을 같이 준다. 따로 말하지 않으면 일본어 원문을 따라 마침표·쉼표를 빼먹는다.
  - 문장이 끝나면 마침표. 명사구·메뉴 항목·이름은 넣지 않는다.
  - 부르는 말 뒤 쉼표(예: 「이츠키, 가자.」).
  - 말줄임표·물결표 뒤에는 마침표를 찍지 않는다.
  - 괄호 속 설명이 문장이면 괄호 안에 마침표를 찍는다.
  - 전각·반각 부호를 어느 쪽으로 쓸지 정한다.
- 태그(색·변수·버튼 아이콘)와 줄 수를 지키는지 기계로 검사한다.
- 텍스트와 그래픽은 다른 세션에서 **병렬로** 진행할 수 있다. 두 쪽 모두 같은 용어집을 본다.

## 6. 그래픽 번역

- 단순한 글자는 Claude도 잘 그린다. 원본 느낌을 살려야 하는 로고나 복잡한 그림은 이미지 생성이 되는 GPT가 유리하다.
- **작업 전에 규칙을 정한다.** 정하지 않으면 AI가 장마다 제멋대로 처리한다.
  - 크기·형식·투명도는 원본과 같아야 한다.
  - 번역문이 원문보다 길거나 짧을 때: 글자 크기 줄이기, 가로 압축 한도, 줄바꿈 허용 여부를 정한다.
  - 원본 글꼴 느낌(굵기·테두리·그림자·그라데이션)을 살린다.
  - 기울어진 글줄은 일자로 쓴 뒤 줄 전체를 원본 각도로 돌린다. 글자마다 기울이지 않는다.
- **순서**: 원본 미리보기와 번역안을 먼저 보여 준다 → 승인 → 작업 → 비교 시트 → 확정.
- **작업 3단계**: 글자 픽셀만 지운다(네모로 오려 내지 않는다) → 바탕을 복원한다 → 한글을 배치한다.
- **비교 시트**(원본 | 지운 뒤 | 한글)를 반드시 받는다. 지운 곳·새 글자 밖에서 바뀐 픽셀이 0인지 수치로 받는다.
- **같은 그림, 같은 시리즈는 묶어서** 톤을 맞춘다. 포스터 원본이 공지·광고·컷신에 축소판으로 다시 쓰이는 경우가 많다.
- **목록 파일 하나를 단일 기준으로** 둔다(완료·건너뜀·작업 대기, 작업자, 사유). 확정본은 한 폴더에만 두고, 확정되면 동결한다. 이전 판과 중간물은 정리한다.

## 7. AI 검수

주입하기 전에 기계 검사와 사람 검사를 나눈다.

- 기계 검사: 태그 보존, 줄 수, 창 폭 넘침, 문장부호 규칙, 용어집 불일치, 그래픽 규격(크기·형식·헤더)
- 사람 검사용 **대조표**: 원문 | 수정 전 | 수정 후. 번역을 고칠 때마다 대조표를 먼저 보고 승인한다.

## 8. 주입·빌드

- 원본과 같은 방식으로 넣는다: 압축 여부, 정렬, 파일 순서, 헤더 값.
- 빌드 결과를 검증한다: 교체한 파일을 다시 읽어 일치하는지, 나머지는 원본과 같은지, 파일 크기 제한(FAT32 4GiB 등)을 넘지 않는지.
- 빌드·주입·기기로 옮기기(SD 복사·카트리지 쓰기 등)는 **사람이 시킬 때만** 한다. AI가 목록을 고칠 때마다 빌드를 돌리면 시간만 쓴다.

## 9. 회귀·멈춤 위험 점검

- 원본과 비교해 바뀐 파일, 크기 변화, 압축 여부, 체크섬을 표로 받는다.
- **바뀐 것을 나눠서 넣고 뺄 수 있게** 빌드한다. 멈춤·크래시가 생기면 하나씩 빼서 원인을 좁히기 위해서다.
  - 나누는 단위는 게임 구조를 따른다. 분야마다 파일·아카이브가 따로면 그 단위로, 롬이나 디스크 이미지 하나라면 빌드 옵션으로 분야를 켜고 끌 수 있게 한다.
  - 구조상 나눌 수 없으면 변경을 작은 단위로 여러 번 나눠 시험한다.
  - 사례: 여러 아카이브로 나뉜 게임에서 전체 빌드가 실기에서 멈췄을 때, 3D 모델 아카이브만 빼니 정상이었다.
- 옛 구성을 다시 시험해야 할 때를 대비해 버전마다 git 커밋을 남긴다. 커밋 시점의 번역문과 도구로 같은 팩을 재현할 수 있다.

## 10. 실행 검수

- 에뮬레이터 또는 실기로 플레이하며 본다.
- 오류는 **스크린샷과 전후 상황**(어느 장면, 무엇을 눌렀는지)을 함께 준다.
- 하나를 고치면 **같은 유형을 전부** 찾아 고치게 한다(예: 넘치는 줄 하나 → 전체 넘침 검사).
- 사용자가 화면에서 본 현상은 사실로 받고 원인부터 찾게 한다. "그럴 리 없다"로 시작하면 시간을 버린다.
  - 사례: 타이틀 로고가 어떤 때는 한글, 어떤 때는 일본어로 보였다. 원인은 로고 영상을 넘기면 정지 그림이 나오고, 가만히 두면 영상 속 원본 로고가 나오는 구조였다.

## 11. 버전·배포

- 검수가 어느 정도 끝나면 버전(v0.1 등)을 붙이고 git 태그를 단다.
- 배포물에는 게임 데이터를 넣지 않는다. 원본에 적용하는 **차분 패치**나 **패처**로 배포한다.
  - 원본 해시가 사람마다 다를 수 있으면(Wii·GC 이미지 등) 이미지 통째 차분보다 **파일 단위 차분 패처**가 맞다.
  - 크기가 유난히 큰 항목(예: 다시 구운 영상)이 있으면 선택 항목으로 나눈다.
- 문서: README(설치법·확인한 실행 환경·크레디트), 폰트 라이선스(OFL 등) 전문.

## 운영 원칙 (전 단계 공통)

1. **사람이 정할 곳에서 멈춘다.** 판본, 진행 여부, 용어집, 그래픽 규칙, 번역 수정, 빌드, 공개는 사람이 정한다.
2. **목록 파일 하나가 기준이다.** 상태를 여러 곳에 적지 않는다.
3. **지우기 전에 대상 목록을 먼저 본다.** 게임 폴더 이름의 `[Game]` 같은 대괄호는 셸·glob에서 패턴으로 읽혀 엉뚱한 파일을 지울 수 있다. 남길 파일은 먼저 다른 곳으로 옮기고 지운다.
4. **배운 것은 기록으로 남긴다.** 형식 구조, 함정, 사용자 선호를 메모리나 문서에 적어 두면 다음 작품이 빨라진다.
5. **병렬 세션은 규칙을 맞춘다.** 작업자 이름, 담당 범위, 결과를 넣는 곳을 정하고, 확정본을 합치는 사람은 한 명(메인 세션)으로 한다.
6. **보고는 사실대로.** 검증하지 않은 것은 검증하지 않았다고 쓴다. 실패는 원인과 함께 바로 알린다.

기종·형식에 따라 해당할 때만 참고한다.

| 분야 | 함정 | 대응 |
|---|---|---|
| 아카이브 | 원본에서 압축돼 있던 파일을 무압축으로 넣으면 실기에서 멈춤(에뮬레이터는 정상) | 원본과 같은 압축으로 넣는다 |
| 아카이브 | 같은 내용 파일이 오프셋을 공유 | 재패킹 때 공유를 유지해야 바이트가 같다 |
| 폰트 | 고정폭 폰트에서 반각 문자가 전각 폭 | 반각 글자 폭만 좁힌다 |
| 폰트 | 한글이 원본 한자보다 위·아래로 치우쳐 잘림 | 원본 한자 기준선에 맞춘다 |
| 폰트 | 글자마다 따로 축소하면 획 굵기가 들쭉날쭉 | 공통 배율·공통 격자로 그린다 |
| 텍스트 | 줄바꿈으로 줄 수가 늘면 고정 창에서 아래가 잘림 | 창별 줄 수 한도를 검사한다 |
| 텍스트 | 일본어식 문장부호 누락, 말줄임표 뒤 마침표 | 번역 요청에 부호 규칙을 넣고 기계로 검사한다 |
| 그래픽 | 같은 그림이 다른 경로에 복사돼 있음 | 원본 해시로 묶어 한 번만 작업하고 복사한다 |
| 그래픽 | 이펙트·파티클 파일 속 글자 텍스처 누락 | 이펙트 컨테이너까지 전수 조사한다 |
| 그래픽 | 글자 테두리·그림자를 빼먹어 밝은 배경에서 안 보임 | 원본 테두리를 측정해 같은 두께로 넣는다 |
| 영상 | 투명도(알파) 영상의 밝기 범위를 좁혀 구움 | 원본과 같은 범위(예: 0~255)로 굽는다 |
| 영상 | 타이틀 로고가 영상 속에 있음 | 정지 그림과 영상 둘 다 확인한다 |
| 배포 | 덤프 방식마다 원본 해시가 다름 | 파일 단위 차분 패처로 배포한다 |
